# ArktsLibraryTestCoverageCheckSkill

对**已鸿蒙化的 ArkTS 库**进行用例覆盖度检视，评估测试用例对公开接口的覆盖程度、测试质量、鸿蒙化特性测试覆盖等关键指标。

> ⚠️ **核心定位**：检视鸿蒙化库的**公开接口测试覆盖情况**，而非追求 100% 的代码行覆盖率。重点评估关键功能是否有测试保障。

---

## 任务参数

| 参数 | 必需 | 说明 |
|------|------|------|
| `repoUrl` | ✅ | Git 仓库地址，支持分支参数 `?branch=xxx` |
| `outputDir` | ✅ | 输出目录绝对路径，存放检视报告 |
| `interfaceDocPath` | ✅ | 接口规格说明文档路径（由 library-interface-analyzer 生成） |
| `repoName` | ✅ | 仓库名称（用于报告标识） |

---

## 输入依赖

本 SKILL 是 ArkTS 仓库检视流程的**第六阶段**（最终 SKILL），依赖：

- **前置 SKILL**: `ArktsLibraryDocumentationQualityCheckSkill`（文档质量检视已完成）
- **输入文件**: `接口规格说明.md`、`文档质量检视报告.md`（位于 outputDir）
- **仓库源码**: 已克隆到 `{outputDir}/source/`

> 💡 **利用前置报告**：参考文档质量检视报告中标记的文档缺失和接口描述不全问题，重点关注这些接口的测试覆盖情况——文档描述不全的接口往往也缺少测试。

## 工作流程

### Phase 1：测试范围识别与鸿蒙代码定位

**通过多维度特征扫描**，智能识别鸿蒙化代码和测试文件：

#### 1.1 扫描策略（优先级递减）

| 扫描维度 | 特征模式 | 权重 | 说明 |
|----------|----------|------|------|
| **测试文件类型** | `*test*.ets`、`*Test*.ets`、`*spec*.ets`、`*test*.ts`、`*Test*.ts` | ⭐⭐⭐ 高 | 鸿蒙测试文件特征 |
| **测试目录** | `test/`、`tests/`、`__tests__/`、`ohosTest/` | ⭐⭐⭐ 高 | 鸿蒙测试目录特征 |
| **鸿蒙源码** | `*.ets` 文件、`module.json5`、`@ohos.*` API | ⭐⭐⭐ 高 | 源码检视范围 |
| **C++ NAPI** | `napi_*` 相关文件 | ⭐⭐ 中 | Native 层绑定 |
| **测试框架配置** | `hypium`、`Devecotest` 配置文件 | ⭐ 低 | 测试框架标识 |

#### 1.2 扫描执行

```bash
# Step 1: 扫描测试文件
find {{outputDir}}/source -type f \( -name "*test*.ets" -o -name "*Test*.ets" -o -name "*spec*.ets" -o -name "*test*.ts" -o -name "*Test*.ts" \)

# Step 2: 找到测试目录
find {{outputDir}}/source -type d \( -name "test" -o -name "tests" -o -name "__tests__" -o -name "ohosTest" \)

# Step 2b: 找到 DEMO/示例目录（用于接口覆盖性评估）
find {{outputDir}}/source -type d \( -name "demo" -o -name "example" -o -name "sample" -o -name "demos" -o -name "examples" -o -name "samples" \)

# Step 3: 扫描鸿蒙源码（用于对照接口覆盖）
find {{outputDir}}/source -type f \( -name "*.ets" -o -name "*.ts" -o -name "*.json5" \)

# Step 4: 扫描 NAPI 相关 C++ 文件
grep -r "napi_" --include="*.cpp" --include="*.h" {{outputDir}}/source || true
```

> `workdir: "{{outputDir}}"`

#### 1.3 代码定位结果分类

```
检视范围判定：
├── 鸿蒙测试代码（必检视）
│   ├── *test*.ets / *Test*.ets   # ArkTS 测试文件 ✅ 检视
│   ├── *test*.ts / *Test*.ts     # TS 测试文件 ✅ 检视
│   ├── *spec*.ets / *spec*.ts    # 规范测试文件 ✅ 检视
│   └── ohosTest 目录下文件        # 鸿蒙单元测试 ✅ 检视
├── DEMO/示例代码（接口覆盖评估）
│   ├── demo/ 目录下文件           # 示例代码 ✅ 检视
│   ├── example/ 目录下文件       # 示例代码 ✅ 检视
│   └── sample/ 目录下文件        # 示例代码 ✅ 检视
├── 鸿蒙源码（用于接口对照）
│   ├── *.ets 文件                # ArkTS 实现 ✅ 对照
│   ├── module.json5              # 模块配置 ✅ 对照
│   └── napi_*.cpp / *.cpp        # Native NAPI 绑定 ✅ 对照
├── 非鸿蒙代码（不检视）
│   ├── 原平台测试文件             ❌ 不检视
│   └── 未包含鸿蒙特征的代码      ❌ 不检视
├── 疑似鸿蒙代码（需验证）
│   ├── 含部分 napi 调用但无完整结构 ⚠️ 进一步检查
```

#### 1.4 判定规则

| 扫描结果 | 判定 | 后续操作 |
|----------|------|----------|
| 发现鸿蒙测试文件 | ✅ 正常检视 | 提取测试覆盖接口清单 |
| 发现鸿蒙源码但无测试文件 | ⚠️ 无测试 | 标注"无鸿蒙化测试"，所有接口视为未覆盖 |
| 仅发现非鸿蒙测试文件 | ⚠️ 测试不匹配 | 标注"仅有原平台测试"，鸿蒙接口视为未覆盖 |
| 未发现鸿蒙特征代码 | ❌ 未鸿蒙化 | 标注"未发现鸿蒙化实现"，评 0 分 |
| 无法访问源码目录 | ❌ 无法检视 | 标注"源码目录不可访问"，评 0 分 |

同时读取 `接口规格说明.md`，提取所有公开接口列表，作为覆盖度评估基准。

### Phase 2：用例覆盖度分析

> **MCP 脚本辅助**：接口覆盖率计算可复用 MCP 脚本工具自动完成：
> - `script_arkts_analyze_demo_coverage`（`MCP/scripts/analyze-demo-coverage.cjs`）→ 计算 DEMO 目录接口覆盖率
> - `script_arkts_analyze_xts_coverage`（`MCP/scripts/analyze-xts-coverage.cjs`）→ 计算 test 目录接口覆盖率
>
> 详细调用方式参见 [MCP工具使用指南](references/MCP_TOOL_USAGE.md)

对测试文件进行覆盖度检视，重点关注以下 5 个维度：

#### 2.1 公开接口覆盖率（维度权重 40%）

> 本维度是覆盖度检视的**核心维度**，直接影响评分。

| # | 检查项 | 扣分 | 说明 |
|---|--------|------|------|
| TC-01 | 核心接口未覆盖 | **-15** | 公开核心功能接口（标注为必须/required）无任何测试 |
| TC-02 | 重要接口未覆盖 | **-10** | 重要公开接口缺少测试用例 |
| TC-03 | 边界场景缺失 | **-8** | 接口缺少边界值/异常输入测试 |
| TC-04 | 可选接口未覆盖 | **-3** | 可选功能接口未测试 |
| TC-05 | 接口参数组合未覆盖 | **-5** | 接口多参数组合场景未测试 |

> **覆盖率计算公式**：
> - 公开接口覆盖率 = (有测试的接口数 / 总公开接口数) × 100%
>
> **覆盖率来源双通道**：接口覆盖率可从以下两个来源分别计算，**任意一个达到 100% 即视为通过**：
> - **DEMO 目录**：DEMO 示例代码中调用的公开接口（通常位于 `demo/`、`example/`、`sample/` 等目录）
> - **test 目录**：测试代码中调用的公开接口（通常位于 `test/`、`tests/`、`__tests__/`、`ohosTest/` 等目录）
>
> 计算方式：分别统计 DEMO 目录和 test 目录中覆盖的公开接口，得到两个覆盖率。只要其中一个达到 100%，接口覆盖率即视为 100%。
>
> **扣分上限**：本维度扣分上限为 -40 分（维度基础分 40 分）

#### 2.2 测试质量（维度权重 20%）

| # | 检查项 | 扣分 | 说明 |
|---|--------|------|------|
| TC-06 | 断言缺失 | **-10** | 测试函数无 assert/expect 断言 |
| TC-07 | 断言过弱 | **-5** | 仅断言不抛异常，未验证正确输出 |
| TC-08 | 测试独立性 | **-8** | 测试间存在数据依赖，无法独立运行 |
| TC-09 | Mock 过度 | **-5** | 过多 Mock 导致测试脱离真实环境 |
| TC-10 | 负面测试缺失 | **-8** | 缺少异常/失败场景测试 |
| TC-11 | 测试数据硬编码 | **-3** | 测试数据全硬编码，未提取为 fixtures |

> **扣分上限**：本维度扣分上限为 -20 分（维度基础分 20 分）

#### 2.3 鸿蒙化特性测试覆盖（维度权重 20%）

| # | 检查项 | 扣分 | 说明 |
|---|--------|------|------|
| TC-12 | 鸿蒙 API 调用未测试 | **-12** | @ohos.* API 调用无测试覆盖 |
| TC-13 | 权限场景未测试 | **-8** | 需权限的 API 无权限场景测试 |
| TC-14 | Lifecycle 测试缺失 | **-10** | ArkTS 组件生命周期未测试 |
| TC-15 | NAPI 测试缺失 | **-10** | Native 模块接口无测试 |
| TC-16 | 跨设备场景未测试 | **-5** | 鸿蒙多设备场景无测试 |
| TC-17 | 鸿蒙配置测试缺失 | **-3** | module.json5 配置未测试 |

> **扣分上限**：本维度扣分上限为 -20 分（维度基础分 20 分）

#### 2.4 测试分类覆盖（维度权重 15%）

> 本维度评估测试的层次覆盖，区分不同类型的测试。

| # | 检查项 | 扣分 | 说明 |
|---|--------|------|------|
| TC-18 | 缺少单元测试 | **-8** | 对独立函数/方法无单元级测试 |
| TC-19 | 缺少集成测试 | **-5** | 对模块间交互无集成级测试 |
| TC-20 | 缺少端到端测试 | **-5** | 对完整功能流程无 E2E 测试 |
| TC-21 | 测试命名不规范 | **-3** | 测试文件/函数命名不符合规范（未含 test/Test/spec 关键词） |
| TC-22 | 测试分类标注缺失 | **-2** | 测试未标注类型（unit/integration/e2e） |

> **扣分上限**：本维度扣分上限为 -15 分（维度基础分 15 分）

#### 2.5 测试基础设施（维度权重 5%）

| # | 检查项 | 扣分 | 说明 |
|---|--------|------|------|
| TC-23 | 测试框架配置缺失 | **-5** | 缺少测试框架（如 @ohos/hypium）配置 |
| TC-24 | 测试脚本缺失 | **-3** | 无测试运行脚本 |
| TC-25 | CI 集成缺失 | **-3** | 无 CI/CD 测试流程配置 |
| TC-26 | 测试数据管理缺失 | **-2** | 缺少测试数据/fixtures 管理 |

> **扣分上限**：本维度扣分上限为 -5 分（维度基础分 5 分）

### Phase 3：用例覆盖度评分计算

基于检视结果进行**严苛评分**（0-100分），采用维度加权扣分制与零容忍规则：

#### 3.1 维度评分规则

| 维度 | 权重 | 基础分 | 扣分上限 | 检查项范围 |
|------|------|--------|----------|------------|
| 公开接口覆盖率 | 40% | 40 | -40 | TC-01~TC-05 |
| 测试质量 | 20% | 20 | -20 | TC-06~TC-11 |
| 鸿蒙化特性测试覆盖 | 20% | 20 | -20 | TC-12~TC-17 |
| 测试分类覆盖 | 15% | 15 | -15 | TC-18~TC-22 |
| 测试基础设施 | 5% | 5 | -5 | TC-23~TC-26 |

**维度得分** = max(0, 基础分 - 该维度累计扣分)

**综合评分** = Σ(各维度得分)，范围 0-100

#### 3.2 零容忍归零规则（叠加于维度扣分之上）

| 规则 | 条件 | 结果 |
|------|------|------|
| 归零规则 1 | 核心接口完全无测试（TC-01 覆盖所有核心接口） | **直接评 0 分** |
| 归零规则 2 | 公开接口覆盖率 < 10%（几乎无接口有测试） | **直接评 0 分** |
| 归零规则 3 | 仓库无任何测试文件 | **直接评 0 分** |
| 归零规则 4 | 未发现鸿蒙化代码 | **0 分** |
| 归零规则 5 | 源码目录不可访问 | **0 分** |
| 归零规则 6 | 接口覆盖率未达 100%（DEMO 和 test 目录均未实现 100% 接口覆盖） | **直接评 0 分** |

#### 3.3 维度子评分独立计算

每个维度独立计算子评分（用于报告中明细展示）：

```
维度子评分 = (维度得分 / 基础分) × 100
```

> 例如：公开接口覆盖率维度得分 28/40，则维度子评分 = 70/100

#### 3.4 严重度映射

问题严重度按扣分值映射：

| 严重度 | 扣分范围 | 说明 |
|--------|----------|------|
| **Critical** | ≥ 10 分 | 致命问题，核心接口无测试或鸿蒙特性无覆盖 |
| **Major** | 5-9 分 | 严重问题，重要测试缺失或测试质量差 |
| **Minor** | ≤ 4 分 | 轻微问题，测试规范性不足 |

#### 3.5 评分等级说明

| 分数区间 | 等级 | 说明 |
|----------|------|------|
| 90-100 分 | 优秀 | 接口覆盖率高、测试质量好、鸿蒙特性有测试保障 |
| 80-89 分 | 良好 | 主要接口有测试，质量尚可，部分鸿蒙特性有覆盖 |
| 70-79 分 | 一般 | 部分接口有测试，测试质量有不足，鸿蒙特性覆盖不充分 |
| 60-69 分 | 较差 | 覆盖率低或测试质量差，鸿蒙特性缺少测试 |
| 50-59 分 | 严重不足 | 核心接口缺少测试保障，鸿蒙化测试几乎缺失 |
| <50 分 | 不可用 | 触发归零规则或几乎所有接口无测试 |
| 0 分 | 完全缺失 | 无任何测试或触发归零规则 |

> ⚠️ **严苛标准**：测试覆盖度是库质量的最后防线。80 分以下即存在明显测试不足，50 分以下视为严重不可用。

### Phase 4：报告生成

在 `{outputDir}` 下生成 `用例覆盖度检视报告.md`，严格遵循 [assets/REPORT_TEMPLATE.md](assets/REPORT_TEMPLATE.md) 中的模板格式。

#### 报告模板结构

报告包含以下章节：

| 章节 | 内容 |
|------|------|
| 一、检视概览 | 仓库信息、接口总数、覆盖率、测试文件数 |
| 二、综合评分 | 综合评分 + 5维度评分表 + 扣分明细 |
| 三、检视范围 | 鸿蒙代码定位结果、文件列表 |
| 四、检视维度明细 | 每个维度的子评分和检查项明细 |
| 五、覆盖度明细 | 每个公开接口的覆盖状态 |
| 六、未覆盖接口清单 | 未覆盖接口列表及说明 |
| 七、改进建议 | P0/P1/P2 优先级改进建议 |

> **重要**：
> 1. 报告必须包含 `**综合评分：XX/100**` 格式（粗体标记、中文冒号），以便后端 `_parseArktsLibraryScore` 函数正确解析评分。
> 2. 每个维度必须包含 `**维度评分：XX/100**` 格式。
> 3. 覆盖度明细必须列出每个公开接口的覆盖状态。

#### 特殊情况处理

| 情况 | 处理方式 | 评分 |
|------|----------|------|
| 未发现任何测试文件 | 报告标注"无鸿蒙化测试文件" | 0 分 |
| 发现测试文件但无断言 | 报告标注"测试文件无有效断言" | 按维度扣分（TC-06） |
| 仅发现原平台测试文件 | 报告标注"仅有原平台测试，鸿蒙接口未覆盖" | 0-30 分 |
| 发现鸿蒙代码但无测试目录 | 报告标注"无测试目录结构" | 按维度扣分 |
| 公开接口覆盖率 < 10% | 报告标注"接口覆盖极低" | 0 分（归零规则） |
| DEMO 和 test 目录均未达 100% 接口覆盖 | 报告标注"接口覆盖率未达 100%"，分别列出 DEMO 和 test 目录的覆盖率 | 0 分（归零规则 6） |
| 扫描到 `.ets` 测试但不在标准目录 | 正常检视，标注实际路径 | 正常评分 |
| 未发现鸿蒙化代码 | 报告标注"未发现鸿蒙化实现代码" | 0 分 |
| 源码目录不可访问 | 报告标注"源码目录不可访问" | 0 分 |
