# 文档标注查询指南

本文档详细说明如何对照鸿蒙 RN 三方库使用文档，标注差异接口的文档覆盖情况。

## 文档来源确定

**文档来源优先级**：

1. **用户传入 `rndocUrl`**：若 `rndocUrl` 不为 null/空，使用该地址作为文档来源
2. **鸿蒙化仓库 README.md**（默认回退）：若 `rndocUrl` 未提供，直接使用 `{ohosAnalysisRoot}/README.md`

根据 `rndocUrl` 的输入类型，分别处理：

| rndocUrl 输入类型 | 判断规则 | 处理方式 | 文档读取路径 |
|----------|----------|----------|----------|
| Git URL | 以 `http://`、`https://`、`git://`、`ssh://` 开头，或以 `.git` 结尾 | 克隆到 `{outputDir}/tmp/rndoc`，按 URL 格式解析规则提取分支/commit/子路径后 checkout | `{outputDir}/tmp/rndoc/{subpath}/` 下的 `.md` 文件 |
| 本地路径 | 路径存在且非 Git URL | 直接读取目录文件 | `rndocUrl` 指向的目录下的 `.md` 文件 |
| Web URL | 以 `http://` 或 `https://` 开头但非 Git 仓库地址（不含 `.git`、`/tree/`、`/blob/`） | 使用 web fetch 获取页面内容 | web fetch 返回的 Markdown 内容 |
| 未提供（null/空） | — | 直接使用鸿蒙化仓库根目录 `README.md` | `{ohosAnalysisRoot}/README.md` |

> ⚠️ 当 `rndocUrl` 为 Git URL 时，克隆必须存放到 `{outputDir}/tmp/rndoc`，禁止克隆到系统临时目录或其他外部路径。

## 定位文档文件

根据文档来源类型，在对应路径中查找匹配的 `.md` 文件：

**rndocUrl 为 Git URL 或本地路径时**：

- 优先精确匹配：`{libraryName}.md`（如 `react-native-touch-id` → `react-native-touch-id.md`）
- 若未命中，尝试去除 `@scope/` 前缀后匹配
- 若仍未命中，列出目录下所有 `.md` 文件，按名称相似度选取最接近的文件
- 若无匹配的 `.md` 文件，列出目录下所有 `.md` 文件，选取最相关的（如 `README.md`）

**rndocUrl 为 Web URL 时**：直接使用 web fetch 获取的内容作为文档。

**rndocUrl 未提供时**：直接读取 `{ohosAnalysisRoot}/README.md`。

**无文档可用**：若以上所有方式均无法获取到文档内容，则所有差异项的"文档是否标注"列统一填 `—`（无文档），并在差异表上方注明"该库暂无使用文档"，**跳过后续查询步骤**。

## 文档结构说明（必读）

文档的章节编号、标题用词、数量都因库而异，**不要假设固定结构**。所有判断都必须基于文档**实际内容**，而非预设的章节编号或关键词。

**定位接口标注的唯一可靠依据**：表格中是否存在 **"HarmonyOS Support" 列**。凡是包含该列的表格，都是接口标注表；不含该列的表格（如纯说明性表格）不携带标注信息。

- 文档中可能有一张或多张包含 "HarmonyOS Support" 列的表格（不同库的表格数量和划分方式不同，需逐张检查）。
- 该列通常为表格最后一列，取值为（大小写不统一）：`yes` / `No` / `no` / `NO` / `partially`。
- 接口章节开头通常有一段固定说明文字，解释上述取值含义：
  > "HarmonyOS Support"列为 yes 表示 HarmonyOS 平台支持该属性；no 则表示不支持；partially 表示部分支持。
- 除接口表格外，文档还可能包含"遗留问题"/"已知问题"类章节（通过 issue 链接补充提及某些接口的已知缺陷），编号和位置不固定，识别时同样以实际内容为准。

> ⚠️ **关键**：文档通过 **"HarmonyOS Support" 列** 标注每个接口在鸿蒙平台的支持情况：
> - `yes` —— 鸿蒙支持
> - `No` / `no` / `NO` —— **鸿蒙不支持**（这就是对"缺失接口"的标注！）
> - `partially` —— 部分支持（这就是对"签名变更/功能差异"的标注！）
>
> **该列的 `No` / `partially` 本身就是差异说明，等同于"已标注差异"，不要再去寻找额外的"不支持"文字描述。**

> ⚠️ **无 "HarmonyOS Support" 列的文档处理**：若文档（如鸿蒙化仓库 README.md）中不包含 "HarmonyOS Support" 列表格，则无法通过表格列进行精确标注判定。此时应通读文档全文，检查文档是否以文字描述、已知问题列表、或其他形式提及差异接口。若文档以任意形式明确提及某接口的差异或不支持，记为 ⚠️ 部分标注；若完全未提及，记为 ❌ 未标注。

## 查询步骤

### 步骤 1：获取文档内容

- **rndocUrl 为 Git URL**：克隆到 `{outputDir}/tmp/rndoc` 后读取本地文件
- **rndocUrl 为本地路径**：直接读取本地文件
- **rndocUrl 为 Web URL**：使用 web fetch 获取内容
- **rndocUrl 未提供**：直接读取 `{ohosAnalysisRoot}/README.md`

> ⚠️ **优先使用本地文件读取**，避免 web fetch。gitcode.com 等平台网页通常只渲染页面框架而不返回 Markdown 原文，web fetch 可靠性低。

### 步骤 2：定位文档文件

按上述规则定位具体的 `.md` 文件。若定位到多个相关文件，合并阅读所有文件内容。

### 步骤 3：读取文档内容

**通读全部内容**，定位所有包含 "HarmonyOS Support" 列的表格行（按列名定位，不依赖章节标题或编号）。逐行判断每行的 "HarmonyOS Support" 列取值。

若文档不包含 "HarmonyOS Support" 列表格，则通读全文检查文字描述形式的差异标注。

### 步骤 4：逐项核对标注

**4a. 名称归一化匹配**

文档中的接口名与源码提取的接口名格式可能不同，匹配前需归一化：
- 方法名：文档写 `clearFormData()`，源码提取 `clearFormData` → 去除 `()` 后缀匹配
- 可选属性：文档写 `saveFormDataDisabled?`，源码提取 `saveFormDataDisabled` → 去除 `?` 后缀匹配
- 版本标记：文档写 `paymentRequestEnabled<sup>13.15.1+</sup>`，源码提取 `paymentRequestEnabled` → 去除 `<sup>...</sup>` 后匹配
- 匹配方式：在文档全文中搜索归一化后的接口名（子串匹配即可）

**4b. 判定规则**

**有 "HarmonyOS Support" 列的文档**：

| 差异类型 | HarmonyOS Support 列值 | 判定结果 |
|----------|----------------------|----------|
| 缺失接口 | `No` / `no` / `NO` | ✅ 已标注（文档明确标注不支持） |
| 缺失接口 | `partially` | ⚠️ 部分标注（文档标注部分支持，但未说明完全缺失） |
| 缺失接口 | `yes` | ⚠️ 部分标注（文档标注支持，与分析结论矛盾，可能文档过时） |
| 新增接口 | 文档中提及且标注为 Harmony 特有 / `yes` | ✅ 已标注 |
| 新增接口 | 文档中提及但未说明为 Harmony 特有 | ⚠️ 部分标注 |
| 签名变更 | `partially` | ✅ 已标注（文档标注部分支持，通常对应签名/功能差异） |
| 签名变更 | `yes` 且文档描述了鸿蒙侧行为差异 | ✅ 已标注 |
| 签名变更 | `yes` 但未描述差异 | ⚠️ 部分标注 |
| 任意类型 | 接口在文档中完全未出现 | ❌ 未标注 |

**无 "HarmonyOS Support" 列的文档（如 README.md）**：

| 差异类型 | 文档中是否提及 | 判定结果 |
|----------|--------------|----------|
| 任意类型 | 文档明确提及该接口在鸿蒙平台不支持/有差异 | ⚠️ 部分标注（文字描述不如表格列精确） |
| 任意类型 | 文档提及该接口但未说明鸿蒙差异 | ⚠️ 部分标注 |
| 任意类型 | 文档完全未提及该接口 | ❌ 未标注 |

**额外检查**：若接口在接口表格中未找到，还需检查标题含「遗留问题」/「已知问题」的章节是否通过 issue 链接提及该接口。若遗留问题中提及，记为 ⚠️ 部分标注。

> 💡 **示例**：`clearFormData` 是缺失接口，在文档「静态方法」章节的表格中找到行 `| clearFormData() | ... | function | No | Android | No |`，HarmonyOS Support 列为 `No` → 判定为 **✅ 已标注**。
