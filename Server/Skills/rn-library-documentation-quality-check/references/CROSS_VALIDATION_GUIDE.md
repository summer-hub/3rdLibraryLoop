# 文档与接口规格交叉验证指南

> 本文件供 `rn-library-documentation-quality-check` 技能在 Phase 2.5 阶段参考使用，详细定义交叉验证的完整流程和比对方法。

> ⚠️ **本环节为强制执行**，不可跳过。文档的终极价值在于准确性——如果文档描述与接口规格不一致，文档不但无用反而有害（误导用户）。

---

## 一、核心思路

本环节以**前置 SKILL `RNLibraryInterfaceAnalyzer` 生成的接口规格说明文档**为权威基准，与用户文档（README/外部 usage-docs）中的 API 描述进行比对，确保文档描述的接口名称、参数签名、返回类型、平台支持状态与接口规格说明文档一致。

> 💡 不需要从源码逐条提取 API 清单——`接口规格说明.md` 已由第一阶段 `RNLibraryInterfaceAnalyzer` 从上游原库和鸿蒙化仓库双仓库中提取完成，包含完整的 API 列表、参数签名、鸿蒙化差异（缺失/新增/变更），直接使用即可。

---

## 二、步骤 2.5.1：加载接口规格说明文档

读取 `{outputDir}/接口规格说明.md`，提取以下结构化信息：

| 提取项 | 对应章节 | 用途 |
|--------|---------|------|
| JS/TS 层导出接口列表（类、方法、属性、签名） | 第 3 章：JS/TS 层导出接口 | 与文档描述的 API 名称/签名比对 |
| 原生模块导出接口（TurboModule/NAPI 方法） | 第 4 章：原生模块导出接口 | 与文档描述的原生 API 比对 |
| 鸿蒙化缺失接口列表 | 第 5 章：5.1 缺失接口 | 验证文档是否标注了这些差异 |
| 鸿蒙化新增接口列表 | 第 5 章：5.2 新增接口 | 验证文档是否描述了鸿蒙特有 API |
| 上游版本号 / 鸿蒙化版本号 | 第 1 章：概述 | 与文档版本号比对 |

```bash
# 确认接口规格说明文档存在
ls {{outputDir}}/接口规格说明.md

# 快速查看文档结构（章节标题）
grep "^## " {{outputDir}}/接口规格说明.md
```

> ⚠️ 若 `{outputDir}/接口规格说明.md` 不存在，记录为 Critical 问题（XC-001），跳过交叉验证环节，在报告中注明"前置接口规格文档缺失，无法进行交叉验证"。

---

## 三、步骤 2.5.2：从用户文档提取描述的 API 清单

从 README、外部 usage-docs 中提取文档声称的接口信息，建立**文档侧 API 清单**：

- 内嵌模式：从 README 提取 API 表格和接口描述，重点关注"接口说明""API Reference""静态方法""属性"等章节中的表格
- 跳转模式：从外部 usage-docs 提取，重点关注外部文档中的接口支持矩阵（HarmonyOS Support 列）

对每个文档描述的 API 项，记录：
- 文档中的方法名 / 属性名
- 文档描述的参数列表（名称、类型、可选性）
- 文档描述的返回类型
- 文档标注的平台支持状态（Yes/No/Partial）
- 来源文件（README / 外部 docs）

---

## 四、步骤 2.5.3：接口规格与文档描述比对

以接口规格说明文档为权威基准，与文档侧 API 清单进行比对：

| 比对方向 | 检查内容 | 对应检查项编号 |
|----------|----------|----------------|
| 规格→文档 | 接口规格中定义的 API 是否在用户文档中有描述 | XC-002 |
| 文档→规格 | 用户文档中描述的 API 是否在接口规格中存在 | XC-003, XC-004 |
| 签名与类型 | 文档描述的参数名/类型/可选性/默认值是否与接口规格一致 | XC-005, XC-006, XC-007 |
| 鸿蒙化差异 | 缺失/新增/变更接口与文档描述是否一致 | XC-008, XC-009, XC-010 |

### 4.1 关键比对逻辑

1. **接口规格中标记为"缺失"的 API**（第 5.1 节），如果用户文档仍标记为支持（Yes）→ **Critical**（误导用户使用不存在的 API）
2. **接口规格中标记为"新增"的 API**（第 5.2 节），如果用户文档未描述 → **Major**（用户不知道鸿蒙特有功能）
3. **接口规格中的签名与文档描述不一致**（参数缺失、返回类型不同）→ **Major/Critical**

### 4.2 比对结果分类

- ✅ **一致**：文档描述与接口规格完全匹配
- ⚠️ **轻微偏差**：参数名或类型存在细微差异但不影响使用（如 `string | null` vs `string | null | undefined`）→ Minor
- ❌ **不一致**：方法名不同、参数缺失、返回类型不匹配、文档描述的 API 不存在 → Major/Critical

## 五、步骤 2.5.4：权限与配置比对

从源码直接提取权限和配置信息（这些不在接口规格说明文档中），与文档描述比对：

```bash
# 提取 module.json5 权限声明
grep -A5 "requestPermissions" {{outputDir}}/source/ohos/src/main/module.json5

# 提取版本号（与接口规格交叉验证）
grep '"version"' {{outputDir}}/source/ohos/oh-package.json5 {{outputDir}}/source/ohos/package.json
```

| 比对项 | 检查内容 | 对应检查项编号 |
|--------|----------|----------------|
| 权限→文档 | module.json5 声明的权限在文档中是否说明 | HA-021 |
| 文档→权限 | 文档说明的权限在 module.json5 中是否声明 | HA-021 |
| 配置步骤 | 文档描述的配置步骤与实际项目结构是否匹配 | XC-011 |
| 版本号 | 文档版本号 vs 接口规格版本号 vs package.json 版本号 | XC-012 |
| 支持矩阵 | 外部文档 API 支持矩阵与接口规格鸿蒙化差异是否一致 | AD-013 |
| 最低版本 | 文档描述的最低 API Version 与代码要求是否一致 | XC-013 |

## 六、步骤 2.5.5：生成交叉验证差异报告

将所有比对差异整理为结构化表格，作为 Phase 2 各维度检视的输入依据：

| # | API 名称 | 比对方向 | 差异类型 | 接口规格 | 文档描述 | 检查项编号 | 严重度 |
|---|----------|----------|----------|----------|----------|-----------|--------|
| 1 | `NetInfo.fetch()` | 签名比对 | 返回类型不一致 | `Promise<NetInfoState>` | `NetInfoState` | XC-006 | Critical |
| 2 | `WebViewNativeConfig` | 鸿蒙化差异 | 缺失接口标记为支持 | 缺失❌ | 文档标记 Yes | XC-008 | Critical |
| 3 | `schemeList` | 规格→文档 | 新增接口未描述 | 新增🆕 | 文档未提及 | XC-009 | Major |

> 完整的交叉验证检查项清单（XC-xxx）参考 [CHECK_CHECKLIST.md](./CHECK_CHECKLIST.md) 第七章。
