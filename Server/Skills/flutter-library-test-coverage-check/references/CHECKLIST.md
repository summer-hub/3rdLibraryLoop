# Flutter 用例覆盖度检视清单

本文档列出 Flutter 三方库用例覆盖度检视的详细检查项，**核心聚焦 Dart 公开接口的覆盖程度**。覆盖率数据由内置脚本自动生成，检视者基于脚本报告进行评分和深度分析。

> ⚠️ **核心定位**：Flutter 三方库对外导出的接口是 **Dart 层定义的**，检视范围包括 `test/` 目录的测试代码和 `example/` 目录的 demo 示例。接口提取和覆盖率匹配由 `scripts/` 目录下的脚本自动完成。

---

## 0. 脚本执行检查

### 0.1 接口提取脚本

| 检查项 | 要求 | 通过条件 |
|--------|------|----------|
| 脚本执行成功 | `flutter-extract-interfaces.cjs` 正常退出 | ✅ 生成 `interface-spec.json` |
| 接口数量 > 0 | 提取到至少 1 个公开接口 | ✅ interfaces 数组非空 |
| 入口文件正确定位 | `lib/<package>.dart` 被识别 | ✅ entryFile 字段正确 |
| 源文件覆盖完整 | export 链可达文件全部收集 | ✅ sources 数组完整 |

### 0.2 XTS 覆盖率脚本

| 检查项 | 要求 | 通过条件 |
|--------|------|----------|
| 脚本执行成功 | `flutter-analyze-xts-coverage.cjs` 正常退出 | ✅ 生成报告 .md |
| 测试目录定位 | 找到 test/ 或 example/test/ | ✅ 报告中源文件数 > 0 |
| 覆盖率数据有效 | 方法级覆盖率已计算 | ✅ 覆盖率总览章节有数值 |
| 未覆盖接口清单 | 未覆盖接口已列出 | ✅ 未覆盖接口详情章节存在 |

### 0.3 Demo 覆盖率脚本

| 检查项 | 要求 | 通过条件 |
|--------|------|----------|
| 脚本执行成功 | `flutter-analyze-demo-coverage.cjs` 正常退出 | ✅ 生成报告 .md |
| Demo 目录定位 | 找到 example/lib | ✅ 报告中源文件数 > 0 |
| 覆盖率数据有效 | 方法级覆盖率已计算 | ✅ 覆盖率总览章节有数值 |
| 未覆盖接口清单 | 未覆盖接口已列出 | ✅ 未覆盖接口详情章节存在 |

## 1. 测试结构检查（满分 15 分）

### 1.1 测试目录结构

| 检查项 | 要求 | 风险等级 | 扣分 |
|--------|------|----------|------|
| test/ 目录存在 | Flutter 项目必须有 test 目录 | 高 | **缺失扣 15 分（致命）** |
| 测试文件数量 | 至少有 1 个测试文件 | 高 | 缺失扣 10 分 |
| 测试文件命名 | 以 `_test.dart` 结尾 | 中 | 不规范扣 3 分/文件 |
| 测试目录组织 | 合理的子目录划分（如 `test/src/`） | 低 | 无组织扣 2 分 |

**标准结构**：

```
project/
├── lib/
│   ├── src/
│   │   ├── feature_a.dart
│   │   └── feature_b.dart
│   └── my_plugin.dart            ← 入口文件，对外导出接口
├── test/
│   ├── src/
│   │   ├── feature_a_test.dart   ← 对应 lib/src/ 的测试
│   │   └── feature_b_test.dart
│   └── my_plugin_test.dart       ← 对应 lib/my_plugin.dart 的测试
├── example/
│   ├── lib/
│   │   └── main.dart             ← demo 示例，调用公开接口
│   └── ...
└── pubspec.yaml
```

> 脚本报告中的"源文件数"可用于快速判断测试文件数量。

### 1.2 example 目录检查（Demo 补充覆盖）

| 检查项 | 要求 | 风险等级 | 扣分 |
|--------|------|----------|------|
| example 目录存在 | 有示例应用展示接口使用 | 中 | 缺失扣 5 分 |
| demo 调用核心接口 | demo 调用了 Dart 公开接口 | 高 | 未调用核心接口扣 3 分 |
| demo 代码可运行 | example 应用可正常编译运行 | 中 | 不可运行扣 2 分 |

> Demo 覆盖数据来自 `flutter-analyze-demo-coverage.cjs` 报告。如果脚本报告显示 Demo 覆盖率 > 0%，说明 demo 确实调用了公开接口。

### 1.3 测试框架配置

| 检查项 | 要求 | 风险等级 | 扣分 |
|--------|------|----------|------|
| flutter_test | pubspec.yaml 配置 flutter_test | 高 | **缺失扣 5 分** |
| mockito | 使用 mockito 进行 mock（或 fake） | 中 | 未使用扣 3 分 |
| test_coverage | 配置测试覆盖率工具（coverage 包） | 低 | 未配置扣 2 分 |
| integration_test | 有集成测试目录（可选） | 低 | 无扣分（可选） |

**pubspec.yaml 标准配置**：

```yaml
dev_dependencies:
  flutter_test:
    sdk: flutter
  mockito: ^5.4.0        # Mock 框架
  build_runner: ^2.4.0   # mockito 代码生成
  coverage: ^1.6.0       # 覆盖率工具
```

## 2. 公开接口覆盖率检查（满分 40 分，核心维度）

> ⚠️ **核心说明**：本维度的覆盖率数据**直接从脚本报告读取**，无需手动计算。详细评分规则参见 [评分规则详解](SCORING_RULES.md)。

### 2.1 覆盖率数据来源

| 数据项 | 来源脚本 | 报告位置 | 用途 |
|--------|----------|----------|------|
| 测试覆盖率 | `flutter-analyze-xts-coverage.cjs` | "覆盖率总览" → "方法级覆盖率" | 一票否决 + 扣分 |
| Demo 覆盖率 | `flutter-analyze-demo-coverage.cjs` | "覆盖率总览" → "方法级覆盖率" | 一票否决 + 豁免 |
| 类级覆盖率 | 两个脚本 | "类级覆盖率"表 | 覆盖核对表 |
| 未覆盖接口 | 两个脚本 | "未覆盖接口详情"章节 | 未覆盖清单 |
| 已覆盖接口 | 两个脚本 | "已覆盖接口详情"章节 | Demo 补充判定 |

### 2.2 接口类型统计口径

脚本在计算覆盖率时**排除**以下类型（不计入覆盖率分母）：

| 排除类型 | 原因 | 报告标注 |
|----------|------|----------|
| `constant` | const/final 常量，只读值无业务逻辑 | "不计入覆盖率" |
| `enumValue` | 枚举常量 | "不计入覆盖率" |
| `constructor` | 实例化入口，Demo/测试中常通过间接方式获得 | "不计入覆盖率" |

**计入覆盖率的类型**：method、property、field、function、type、variable

### 2.3 一票否决规则判定

```
判定流程：
1. 读取 XTS 覆盖率（来自脚本报告）
2. 读取 Demo 覆盖率（来自脚本报告）
3. 判定：
   - XTS 覆盖率 = 100% → ✅ 豁免一票否决
   - Demo 覆盖率 = 100% → ✅ 豁免一票否决
   - 两者均 < 100% → ❌ 触发一票否决，直接 0 分
```

### 2.4 测试覆盖率扣分规则

> 仅在一票否决规则未触发时适用。

| 覆盖率范围 | 扣分值 | 说明 |
|------------|--------|------|
| 100% | 0 分 | 完全覆盖（✅ 豁免一票否决） |
| ≥ 80% | -4 分 | 覆盖率较高 |
| 60%-79% | -8 分 | 中等缺失 |
| 40%-59% | -16 分 | 严重缺失 |
| 20%-39% | -24 分 | 严重缺失 |
| 10%-19% | -32 分 | 非常严重缺失 |
| 5%-9% | -38 分 | 几乎无测试 |
| < 5% | **直接 0 分** | 致命缺失 |

### 2.5 Demo 补充覆盖检查

对比 XTS 报告和 Demo 报告的未覆盖接口，确定 Demo 补充覆盖范围：

```
Demo 补充覆盖 = XTS 未覆盖接口 ∩ Demo 已覆盖接口

抵扣规则：
- 每个被 Demo 覆盖的未测试接口，抵扣 50% 缺失扣分
- 总抵扣上限 5 分
```

### 2.6 未覆盖接口清单生成

从脚本报告提取未覆盖接口，按影响程度分类：

| 分类 | 判定条件 | 来源 |
|------|----------|------|
| **致命缺失** | XTS 未覆盖 ∩ Demo 未覆盖 | 两份报告未覆盖列表的交集 |
| **严重缺失** | XTS 未覆盖 ∩ Demo 已覆盖 | XTS 未覆盖 - Demo 未覆盖 |
| **中等缺失** | 边缘功能未覆盖 | 根据接口重要性判断 |

### 2.7 覆盖率不足原因分析（不减免扣分）

| 原因类型 | 典型场景 | 扣分处理 |
|----------|----------|----------|
| **平台通道限制** | BLE/硬件依赖 MethodChannel | **不减免**，应通过 mock 测试 |
| Mock 机制缺失 | 未创建 MethodChannel mock | **严苛扣分**，测试设计缺陷 |
| 测试设计遗漏 | 纯 Dart 逻辑未测试（如 Guid） | **严苛扣分**，无借口 |
| 代码复杂度高 | 接口逻辑复杂 | **不减免**，复杂更需测试 |
| 开发者懒惰 | 未重视测试 | **严苛扣分** |

> ⚠️ **重要**：Flutter 提供了完整的测试支持（`MethodChannel.setMockMethodCallHandler`），即使是依赖平台通道的接口也应通过 mock 进行测试验证。**不应以"平台依赖"为借口减免扣分**。

## 3. 测试场景覆盖检查（满分 25 分）

### 3.1 测试场景分类（严苛扣分）

| 场景类型 | 检查内容 | 风险等级 | 扣分 |
|----------|----------|----------|------|
| **正常场景** | 测试正常输入和预期输出 | 高 | 缺失扣 5 分 |
| **异常场景** | 测试异常输入、错误处理、超时、权限缺失 | 高 | **缺失扣 8 分** |

| **并发场景** | 测试并发调用、多设备连接、并发读写 | 高 | 缺失扣 7 分 |

| 异常类型 | 检查项 | 风险等级 | 扣分 |

## 4. 测试代码质量检查（满分 20 分）

### 4.1 测试命名规范

| 检查项 | 要求 | 风险等级 | 扣分 |
|--------|------|----------|------|
| 测试组命名 | 使用 `group()` 组织相关测试 | 中 | 未使用扣 3 分 |
| 测试描述清晰 | 描述测试目的和预期（如 "should return X when Y"） | 高 | 不清晰扣 2 分/测试 |
| BDD 风格 | 使用 should/when/then 模式命名 | 低 | 未使用扣 1 分 |

**正确示例**：

```dart
group('BluetoothDevice', () {
  group('connect', () {
    test('should connect successfully when device is available', () async {
      // ...
    });

    test('should throw TimeoutException when connection times out', () async {
      // ...
    });
  });
});
```

### 4.2 测试独立性

| 检查项 | 要求 | 风险等级 | 扣分 |
|--------|------|----------|------|
| 无顺序依赖 | 测试可任意顺序运行 | 高 | **有依赖扣 5 分** |
| 无共享状态 | 测试间不共享可变状态 | 高 | 有共享扣 4 分 |
| 正确清理 | setUp/tearDown 正确使用 | 高 | **未使用扣 6 分** |
| 无外部依赖 | 不依赖网络/外部服务（或 mock） | 高 | **有依赖扣 5 分** |

### 4.3 setUp/tearDown 使用示例

```dart
group('FlutterBluePlus', () {
  setUp(() async {
    // 每个测试前初始化
    TestWidgetsFlutterBinding.ensureInitialized();
    MethodChannel.setMockMethodCallHandler(
      FlutterBluePlus.methodChannel,
      (call) async => null,
    );
  });

  tearDown(() {
    // 每个测试后清理 mock
    MethodChannel.setMockMethodCallHandler(
      FlutterBluePlus.methodChannel,
      null,
    );
  });

  test('adapterStateNow should return current state', () {
    // 测试代码...
  });
});
```

### 4.4 测试可重复性

| 检查项 | 要求 | 风险等级 | 扣分 |
|--------|------|----------|------|
| 结果一致 | 多次运行结果相同 | 高 | 不一致扣 4 分 |
| 无随机数据 | 使用固定测试数据 | 高 | 有随机扣 3 分 |
| 无时间依赖 | 不依赖当前时间（或 mock） | 中 | 有依赖扣 2 分 |

## 5. 评分汇总表

| 维度 | 满分 | 扣分上限 | 核心检查项 | 数据来源 |
|------|------|----------|------------|----------|
| 测试结构完整性 | 15 | -15 | 测试目录、文件、框架配置 | 人工 + 脚本报告 |
| 公开接口覆盖率 | 40 | **-40** | **核心：脚本报告的覆盖率数据** | 脚本报告 |
| 测试场景覆盖 | 25 | -25 | 正常、异常、边界、并发场景 | 人工分析 |
| 测试代码质量 | 20 | -20 | 命名、独立性、可重复性、清理 | 人工分析 |
| **总计** | **100** | **-100** | **累计扣分 > 60 → 直接 0 分** | - |

**特殊规则**：
- 无任何测试文件 → **直接 0 分**
- **接口覆盖率未达 100% → 直接 0 分**（测试覆盖率或 Demo 覆盖率任意一个达到 100% 即可豁免）
- 累计扣分超过 60 分 → **直接 0 分**
