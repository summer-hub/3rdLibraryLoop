# acceptance-check SKILL — 任务准出审核

## 任务参数

| 参数 | 必需 | 说明 |
|------|------|------|
| `taskDescription` | ✅ | 审核任务描述（含原始任务、验收标准、编排结果） |
| `skillDir` | ✅ | 本 SKILL 目录绝对路径 |
| `workDir` | ✅ | 任务工作目录，包含所有步骤产物 |
| `reportPath` | ✅ | 审核报告输出路径 |
| `summaryPath` | ✅ | 审核摘要输出路径 |

---

## 工作流程概览

```
Phase 1: 产物收集 → Phase 2: 逐条标准评估 → Phase 3: 准出结论 → Phase 4: 报告生成
```

---

## Phase 1：产物收集

### 1.1 扫描工作目录

读取 `workDir` 目录下所有步骤产物文件：

- `stepId{N}_result_{loop}.md` — 各步骤的执行结果报告
- `stepId{N}_Summary_{loop}.md` — 各步骤的执行摘要
- 其他生成的文档/报告文件

> 详细文件格式参见 [产物收集指南](references/PHASE1_ARTIFACT_COLLECTION.md)

### 1.2 解析审核任务描述

从 `taskDescription` 中提取：

- **原始任务描述** — 任务的核心目标
- **任务级验收标准** — 需要逐条验证的标准列表（含 id、criterion、type、verification）
- **编排结果摘要** — 步骤执行状态、成功/失败统计

### 1.3 汇总产物清单

将所有步骤产物按 stepId 和 loopCount 排序，形成产物清单供后续评估使用。

---

## Phase 2：逐条标准评估

### 2.1 对照验收标准

对每个任务级验收标准，检查产物是否满足：

```
对于每个验收标准 [ac{id}]:
  1. 读取该标准的内容 (criterion) 和验证方式 (verification)
  2. 在产物中查找相关证据
  3. 根据 verification 描述的验证方式执行检查
  4. 记录评估结论：满足 / 未满足
  5. 记录支持证据
```

### 2.2 验证方式分类

根据标准的 `type` 字段采用不同验证策略：

| type | 验证策略 |
|------|---------|
| `output` | 检查产物文件是否存在、内容是否完整 |
| `quality` | 检查产物质量是否达标（如报告覆盖维度、分析深度） |
| `performance` | 检查性能指标是否满足（如扫描覆盖率、执行时间） |
| `compliance` | 检查是否符合规范标准（如编码规范、格式要求） |

> 详细评估规则参见 [验收标准评估指南](references/PHASE2_CRITERIA_EVALUATION.md)

### 2.3 关键声明核验规则

对关键声明（分支血缘、产物存在、依赖版本、测试结果）执行核验时，必须遵守：

1. **证据三角验证**：验收判定禁止仅凭前序步骤报告的"成功"结论，关键声明必须与实物产物（文件存在性/大小/时间戳）、现场 git/文件查询（如 `git merge-base` 验证分支血缘、直接读依赖清单原文）交叉验证；
2. **依赖版本核验**：先读版本分析报告确认包架构（re-export / 源内复制 / fork），re-export 架构下区分适配包自身 `version` 字段与 `dependencies` 中的上游版本（二者语义不同）；依赖残留区分框架/运行时依赖（阻断项）与 dev 工具依赖滞后（记录项），未阻断项必须如实写入报告"遗留记录"节；
3. **汇总指标分解**：验收标准含汇总数字（如 154/154、95/95）时，必须分解至报告分项逐项对账（如 59+85+10），防止口径错配；
4. **扫描执行安全**：核验类扫描（版本残留/引用检查）必须排除 node_modules/oh_modules/lock 文件/*.har/*.hap/.git，限定依赖清单文件白名单，优先使用 rg（grep 全量扫描在大仓库实测 120s 超时）；
5. **自动生成产物权威级**：链路中自动生成的 diff/扫描件若在后续人工分析报告中被修正，验收一律以修正结论件为准，自动件仅作参考。

> 详细核验检查单、判定维度与示例参见 [关键声明核验规则指南](references/PHASE2_EVIDENCE_VERIFICATION.md)

---

## Phase 3：准出结论

### 3.1 汇总评估结果

```
准出结论 = 所有验收标准均满足 ? "通过" : "未通过"
```

### 3.2 生成改进建议

如果准出未通过，针对每个未满足的标准生成改进建议：

- 明确指出哪个标准未满足
- 提供具体的修复方向
- 建议需要重新执行或补充的步骤

---

## Phase 4：报告生成

### 4.1 审核报告格式

将审核结果写入 `reportPath` 指定的文件，格式如下：

```markdown
# 准出审核报告

## 准出结论
通过

（或：未通过）

## 审核概要
- 任务 ID: {taskId}
- 循环次数: 第 {loopCount+1} 次循环
- 审核时间: {timestamp}
- 验收标准总数: {N}
- 满足数量: {M}
- 未满足数量: {N-M}

## 逐条标准评估

### [ac1] (output) 验收标准描述
- **结论**: 满足
- **证据**: {在产物中找到的证据}
- **说明**: {补充分析}

### [ac2] (quality) 验收标准描述
- **结论**: 未满足
- **证据**: {缺失的内容或不达标的分析}
- **说明**: {具体问题}

...

## 改进建议
（仅在未通过时提供）
1. {改进建议1}
2. {改进建议2}

## 遗留记录
（如有：核验中发现的非阻断遗留项）
- {遗留项描述 + 风险定性 + 处置建议}
```

### 4.2 审核摘要格式

将摘要写入 `summaryPath` 指定的文件：

```markdown
# 审核摘要

## 结论
{通过/未通过}

## 关键发现
{主要发现和结论}

## 未满足标准
（如有）
- {未满足标准列表}
```

---

## 输出要求

1. 审核报告必须包含 `## 准出结论` 字段，值为 `通过` 或 `未通过`
2. 审核报告必须逐条列出每个验收标准的评估结论
3. 未通过时必须提供改进建议
4. 报告和摘要文件必须写入指定路径
5. 核验中发现的非阻断遗留项必须如实记录在报告"遗留记录"节（含风险定性），不得隐藏不报，也不得因非阻断遗留项直接判未通过
