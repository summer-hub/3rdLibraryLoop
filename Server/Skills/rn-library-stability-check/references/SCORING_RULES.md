# 评分规则详细说明

> 本文档包含稳定性检视的完整评分规则，包括维度评分公式、归零规则、严重度映射和评分等级。

---

## 1. 维度评分公式

采用**严苛扣分制**，每个维度独立计算扣分后汇总：

| 维度 | 基础分 | 扣分上限 | 检查项范围 | 说明 |
|------|--------|----------|------------|------|
| 异常处理完整性 | 25 | -25 | E-01~E-06 | 各项扣分叠加，维度得分不低于 0 |
| 资源释放安全性 | 20 | -20 | R-01~R-05 | 各项扣分叠加，维度得分不低于 0 |
| 并发安全 | 20 | -20 | C-01~C-03 | 各项扣分叠加，维度得分不低于 0 |
| ArkTS 生命周期 | 10 | -10 | L-01~L-02 | 各项扣分叠加，维度得分不低于 0 |
| NAPI 跨语言调用 | 15 | -15 | N-01~N-05 | 各项扣分叠加，维度得分不低于 0 |
| C++ 内存管理 | 10 | -10 | M-01~M-03 | 各项扣分叠加，维度得分不低于 0 |

### 计算公式

```
维度得分 = max(0, 基础分 - 该维度累计扣分)

综合评分 = Σ(各维度得分) - 调用链完整性扣分
```

- 综合评分范围：0-100
- **调用链完整性**（CH-01~CH-03）的扣分在维度汇总后**额外扣减**，不占基础分
- 调用链完整性扣分可能导致综合评分低于 0，此时取 0

### 计算示例

```
异常处理完整性：25 - (10 + 8 + 0 + 0 + 0 + 0) = 7
资源释放安全性：20 - (10 + 0 + 0 + 0 + 0) = 10
并发安全：      20 - (0 + 0 + 0) = 20
ArkTS 生命周期：10 - (8 + 0) = 2
NAPI 跨语言：   15 - (0 + 0 + 0 + 0 + 0) = 15
C++ 内存管理：  10 - (0 + 0 + 0) = 10
维度汇总 = 7 + 10 + 20 + 2 + 15 + 10 = 64
调用链扣分 = -10（CH-01 触发）
综合评分 = 64 - 10 = 54
```

## 2. 特殊归零规则

归零规则**叠加于维度扣分之上**，触发任一规则则综合评分直接为 0 分：

| 规则 | 条件 | 结果 | 说明 |
|------|------|------|------|
| 归零规则 1 | Critical 级别问题 ≥ 5 个 | **直接评 0 分** | 致命问题密集，稳定性不可接受 |
| 归零规则 2 | Critical ≥ 3 个 + Major ≥ 4 个 | **直接评 0 分** | 严重问题组合触发，风险极高 |
| 归零规则 3 | 关键路径异常处理完全缺失（≥ 3 个关键 API 调用无 try-catch） | **直接评 0 分** | 核心路径无防护，崩溃风险极高 |
| 归零规则 4 | NAPI 引用管理完全不匹配（创建远多于释放） | **直接评 0 分** | Native 内存泄露不可控 |
| 归零规则 5 | 未发现鸿蒙化代码 | **0 分** | 无检视对象 |
| 归零规则 6 | 源码目录不可访问 | **0 分** | 无法执行检视 |

### 归零规则判定流程

```
1. 完成所有维度检查后，统计 Critical 和 Major 数量
2. 依次检查归零规则 1~4
3. 若任一规则触发 → 综合评分 = 0，报告标注触发规则
4. 若无归零规则触发 → 按维度评分公式计算
5. 归零规则 5/6 在 Phase 1 即可判定，提前终止流程
```

## 3. 严重度映射

问题严重度按**单次扣分值**映射，用于问题清单分类和改进建议优先级排序：

| 严重度 | 扣分范围 | 说明 | 报告标注 |
|--------|----------|------|----------|
| **Critical** | ≥ 8 分 | 致命问题，可能导致崩溃或严重资源泄露 | P0 |
| **Major** | 5-7 分 | 严重问题，影响系统稳定性 | P1 |
| **Minor** | ≤ 3 分（含负数） | 轻微问题，建议改进 | P2 |

## 4. 评分等级说明

| 分数段 | 等级 | 说明 | 改进建议 |
|--------|------|------|----------|
| 90-100 | 优秀 | 异常处理完善，资源管理规范，无稳定性风险 | 维持现有质量标准 |
| 80-89 | 良好 | 存在少量 Minor 问题，不影响核心稳定性 | 建议修复 Minor 问题 |
| 70-79 | 一般 | 存在 Major 级别问题需关注，有一定风险 | 修复 Major 问题后可提升至良好 |
| 60-69 | 较差 | 存在 Critical 级别问题，稳定性堪忧 | 必须修复 Critical 问题 |
| <60 | 严重不足 | 多个 Critical 问题，崩溃/泄露风险极高 | 全面重构稳定性设计 |
| 0 | 不可用 | 触发归零规则或完全缺失稳定性设计 | 需要从头实现稳定性保障 |

## 5. 特殊情况评分

| 情况 | 评分 | 报告标注 |
|------|------|----------|
| 未发现 `.ets` 文件和鸿蒙 API 特征 | 0 分 | "未发现鸿蒙化实现代码" |
| 仅发现目录名含 `ohos` 但无代码文件 | 0-30 分 | "鸿蒙化代码疑似缺失" |
| 发现鸿蒙代码但解析失败 | 0 分 | "鸿蒙代码解析失败"并说明原因 |
| Critical 问题 ≥ 5 个 | 0 分 | "存在严重稳定性风险"（归零规则 1） |
| 扫描到 `.ets` 但不在 `ohos/` 目录 | 正常评分 | 标注实际路径 |
