# XTS 用例描述模板

本文档提供 XTS 用例描述的标准模板和编写规范，供生成技能参考。

---

## 一、文档整体模板

```markdown
# ohos_鸿蒙ArkTs原生库名 XTS 用例描述

## 概述

- **库名称**：鸿蒙ArkTs原生库名称
- **文档生成时间**：YYYY-MM-DD
- **基于文档**：接口规格文档名称
- **用例总数**：总数 N
- **可测试接口数**：可测试接口数量
- **不可测试接口数**：不可测试接口数量
- **功能覆盖模块**：模块列表

## 接口可测试性分析

### 可测试接口列表

| 接口名称 | 接口签名 | 可测试原因 |
|---------|---------|-----------|
| interfaceA | function(param: Type): ReturnType | 纯函数，返回值可验证 |
| interfaceB | class.method(param: Type): void | 状态变化可通过其他接口验证 |

### 不可测试接口列表

| 接口名称 | 接口签名 | 不可测试原因 |
|---------|---------|-------------|
| interfaceX | function(): void | 涉及 UI 操作，无法通过执行结果验证 |
| interfaceY | function(): void | 仅日志输出，结果不可验证 |

## 用例索引表

| 用例序号 | 用例名称 | 涉及接口 | 模块归属 |
|---------|---------|---------|---------|
| 001 | 用例名称 A | interfaceA, interfaceB | 模块 X |
| 002 | 用例名称 B | interfaceC | 模块 Y |
| ... | ... | ... | ... |

## XTS 用例详细描述

### 用例序号：001

**用例名称**：用例名称 A

**用例描述**：
详细描述这个用例的功能和目的。要求能够帮助开发者理解：
1. 这个用例要验证什么功能
2. 为什么需要这个测试
3. 测试的核心场景是什么

**用例预期结果**：
列出具体的预期结果，帮助开发者验证：
1. 调用接口 A 后，返回值应为预期值
2. 调用接口 B 后，状态应发生变化
3. ...

**对应的函数接口**：
- `interfaceA(param: Type): ReturnType`
  - 功能：接口功能描述
  - 在本用例中的作用：说明该接口在用例中的使用目的
- `interfaceB(param: Type): void`
  - 功能：接口功能描述
  - 在本用例中的作用：说明该接口在用例中的使用目的
  - 与其他接口的关联：说明与 interfaceA 的调用顺序或依赖关系

---

### 用例序号：002
...
```

## 二、单个用例详细模板

### 2.1 正向用例模板（单接口）

```markdown
### 用例序号：001

**用例名称**：基础计算功能验证

**用例描述**：
验证库的核心计算功能是否正确实现。该用例通过调用 `calculate` 方法，传入合法的计算参数，验证返回的计算结果是否符合预期，确保计算逻辑的正确性和准确性。

**用例预期结果**：
1. 调用 `calculate(10, 20)` 后，返回值应为 `30`
2. 调用 `calculate(-5, 5)` 后，返回值应为 `0`
3. 调用 `calculate(0, 0)` 后，返回值应为 `0`
4. 所有返回值类型符合接口定义（number 类型）

**对应的函数接口**：
- `calculate(x: number, y: number): number`
  - 功能：对两个数值进行加法计算
  - 在本用例中的作用：验证计算逻辑的正确性
```

```markdown
### 用例序号：002

**用例名称**：配置管理完整流程验证

**用例描述**：
验证配置管理功能的完整流程，包括配置设置、获取、清除三个步骤。该用例通过协同调用 `setConfig`、`getConfig`、`clearConfig` 三个接口，验证配置管理功能的完整性和一致性，确保配置能够正确设置、读取和清除。

5. 整个流程无异常抛出，状态变化符合预期

**对应的函数接口**：

- `getConfig(): Config | null`
  - 功能：获取当前配置对象

- `clearConfig(): void`
  - 功能：清除当前配置
  - 在本用例中的作用：作为流程第三步，清除已设置的配置
  - 与其他接口的关联：清除 setConfig 设置的配置，通过 getConfig 验证清除效果
```

## 三、用例编写规范要点

### 3.1 用例名称命名规范

- ✅ **简洁明确**：以功能描述为基础，清晰表达用例目的
- ✅ **动词开头**：如"验证"、"测试"、"检查"
- ❌ **避免模糊**：如"功能测试"、"一般测试"
- ❌ **避免过长**：建议不超过 20 个字符

**命名示例对比：**

| 好的命名 | 不好的命名 |
|---------|-----------|
| 基础计算功能验证 | 测试一下计算 |
| 配置管理完整流程验证 | 配置功能测试 |
| 参数非法输入验证 | 异常测试 |

### 3.2 用例描述编写规范

- ✅ **详细完整**：说明用例的目的、测试场景、验证重点
- ✅ **逻辑清晰**：按步骤描述测试流程
- ✅ **帮助理解**：让开发者明白为什么需要这个测试

**描述模板：**

```
验证 [功能名称] 的 [核心能力] 是否正确实现。
该用例通过 [调用方式]，传入 [参数类型]，
验证 [返回值/状态变化/异常抛出] 是否符合预期，
确保 [功能特性] 的 [质量属性]。
```

### 3.3 用例预期结果编写规范

- ✅ **具体可验证**：列出明确的预期值、状态、异常类型
- ✅ **覆盖全面**：包括正常结果和异常情况
- ✅ **可量化**：尽量使用具体数值、字符串、状态标识

**预期结果编写要点：**

1. **返回值验证**：明确预期返回值（具体值或类型）
2. **状态验证**：明确状态变化（如配置已清除）
3. **异常验证**：明确异常类型和错误码
4. **类型验证**：明确返回值类型是否符合定义

### 3.4 多接口关联说明规范

当用例包含多个接口时，必须说明：

1. **每个接口的功能**：简述接口作用
2. **在本用例中的作用**：说明该接口在用例中的使用目的
3. **与其他接口的关联**：说明调用顺序、依赖关系、验证关系

**关联说明示例：**

```markdown
- `interfaceA()`
  - 在本用例中的作用：作为流程第一步，设置初始状态
- `interfaceB()`
  - 在本用例中的作用：验证 interfaceA 的设置结果
  - 与其他接口的关联：依赖于 interfaceA 设置的状态，用于验证结果
- `interfaceC()`
  - 在本用例中的作用：作为流程最后一步，清除状态
  - 与其他接口的关联：清除 interfaceA 设置的状态，通过 interfaceB 验证清除效果
```

## 五、不可测试接口说明模板

当接口不可测试时，在"接口可测试性分析"部分详细说明原因：

```markdown
### 不可测试接口列表

| 接口名称 | 接口签名 | 不可测试原因 |
|---------|---------|-------------|
| renderUI | function(): void | 涉及 UI 组件创建和渲染，无法通过执行结果验证 |
| logMessage | function(msg: string): void | 仅日志输出，无返回值和状态变化，结果不可验证 |
| onEvent | function(callback: Function): void | 回调触发依赖外部事件，不可控且不可验证 |
```

**不可测试原因分类：**

1. **UI 相关**：涉及 UI 操作、组件创建、界面渲染
2. **输出型**：仅日志输出、无返回值、无状态变化
3. **外部依赖**：依赖不可控外部因素（网络、传感器、系统事件）
4. **回调型**：回调触发条件不可控或不可验证
