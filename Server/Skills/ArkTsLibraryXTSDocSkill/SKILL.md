# 鸿蒙ArkTs原生库未覆盖接口 XTS 用例生成

本 Skill 读取 XTS 覆盖率报告中的未覆盖接口清单，自动判断接口可测试性，为可测试接口生成标准化 XTS 用例描述文档，100% 覆盖所有未覆盖的可测试接口。

> ⚠️ **核心约束**：
> 1. 仅生成纯函数的 XTS 用例描述，不生成需要 UI 操作、无法通过执行结果验证的用例
> 2. 所有用例内容基于覆盖率报告中真实存在的接口签名和功能描述，严禁捏造
> 3. 100% 覆盖所有未覆盖的可测试接口

---

## 适用场景

- 为鸿蒙ArkTs原生库填补 XTS 覆盖率缺口
- 生成可执行的 XTS 用例描述文档
- 评估库接口的可测试性
- 配合 ArkTsLibraryInterfaceSpecSkill + ArkTsLibraryXTSCoverageSkill 实现"接口分析 → XTS 覆盖率分析 → 缺口用例规划"完整链路

## 任务参数

| 参数 | 必需 | 说明 |
|------|------|------|
| `xtsCoverageReportPath` | ✅ | XTS 覆盖率报告绝对路径（由 ArkTsLibraryXTSCoverageSkill 生成，含未覆盖接口清单及签名） |
| `outputDir` | 可选 | 输出目录，默认放置在覆盖率报告所在目录 |

### 输入异常处理

| 异常情况 | 处理方式 |
|---------|---------|
| 覆盖率报告不存在或无法读取 | 停止执行，向用户提示错误 |
| 未覆盖接口清单为空（覆盖率 100%） | 生成空文档，标注"所有接口已覆盖，无需补充" |
| 无法确定库名称 | 使用默认命名 `Unknown未覆盖接口XTS用例描述.md` |

## 工作流程

### 阶段一：读取 XTS 覆盖率报告并提取未覆盖接口

#### 1.1 读取覆盖率报告

```
执行步骤：
1. 使用 read_file 读取 {{xtsCoverageReportPath}} 全文
2. 提取库名称（用于输出文件命名）
3. 提取当前 XTS 覆盖率（用于概述中标注补充前后对比）
```

#### 1.2 提取未覆盖接口清单

定位覆盖率报告「未覆盖接口清单」章节，提取每个未覆盖接口：

| 提取字段 | 来源列 | 用途 |
|---------|--------|------|
| 接口名称 | `方法/属性` 列 | 用例命名 |
| 完整签名 | `签名` 列 | 用例预期结果中标注精确调用方式 |
| 接口类型 | `类型` 列 | 可测试性判断依据 |
| 功能描述 | `功能描述` 列 | 用例描述的依据 |
| 所属类 | `### {ClassName}` 子标题 | 分组依据 |

#### 1.3 建立未覆盖接口能力清单（内部工作记录）

```
未覆盖接口清单（不写入输出文件）：
┌─────────────────────────────────────────────────────┐
│ 类 ImageKnife                                        │
│   - 方法 setMaxPreCreateNodeCount(maxCount): void    │
│     功能: 设置预创建组件最大数量                       │
│   - 方法 reload(requestId): void                     │
│     功能: 重新加载请求                                 │
│ ...                                                  │
│                                                      │
│ 未覆盖接口总数: N                                     │
│ 当前 XTS 覆盖率: X%                                  │
│ 补充后预期覆盖率: 100%                                │
└─────────────────────────────────────────────────────┘
```

### 阶段二：接口可测试性判断

#### 2.1 可测试性判断标准

根据以下标准判断每个未覆盖接口是否可以生成 XTS 用例描述：

**✅ 可生成 XTS 用例的接口特征：**
1. **纯函数**：输入相同参数，输出结果可预测、可重复
2. **无 UI 操作**：不涉及 UI 组件的创建、渲染、交互
3. **结果可验证**：可通过返回值、状态变化、回调结果等判断功能是否正确实现
4. **无外部依赖限制**：不依赖不可控的外部因素（如网络请求需 Mock、传感器需模拟器支持）

**❌ 不可生成 XTS 用例的接口特征：**
1. **涉及 UI 操作**：如创建组件、触发 UI 事件、渲染图形界面
2. **依赖外部不可控因素**：如实时网络请求、硬件传感器、系统广播
3. **结果不可验证**：如回调未定义、异步操作无返回值、副作用不可观测
4. **纯展示型接口**：如仅用于展示信息、不执行具体功能

#### 2.2 接口分类标记

对每个未覆盖接口进行分类标记：

```
接口分类示例：
┌─────────────────────────────────────────────────────┐
│ 接口名称          │ 可测试性 │ 原因说明                │
├─────────────────────────────────────────────────────┤
│ calculate(x, y)   │ ✅ 可测试 │ 纯函数，返回计算结果     │
│ renderUI()        │ ❌ 不可测 │ 涉及 UI 操作            │
│ fetchData(url)    │ ⚠️ 可测试 │ 需 Mock 网络请求后验证   │
│ logMessage(msg)   │ ❌ 不可测 │ 仅日志输出，不可验证      │
│ setConfig(cfg)    │ ✅ 可测试 │ 配置后可通过 getConfig 验证│
└─────────────────────────────────────────────────────┘
```

对于 `⚠️ 可测试（需额外条件）` 的接口，在用例描述中注明测试前提条件（如需要 Mock 网络请求）。

### 阶段三：XTS 用例规划

#### 3.1 用例设计原则

遵循以下原则规划 XTS 用例：

1. **功能覆盖**：每个可测试接口至少有 1 个正向用例
2. **接口关联**：一个用例可包含多个关联接口，展示协同使用方式
3. **预期明确**：每个用例必须有明确、可验证的预期结果
4. **描述清晰**：用例描述需帮助开发者理解功能和实现方式
5. **空值覆盖**：每个可测试接口至少有 1 个空值/null/undefined 输入用例
6. **异常/边界值覆盖**：每个可测试接口至少有 1 个异常参数或边界值输入用例
7. **大数据覆盖**：对于接受数组、字符串、对象等集合类型参数的接口，至少有 1 个大数据量输入用例

#### 3.2 多接口用例设计

**何时将多个接口放在同一用例中：**
- 接口之间存在明显的调用依赖关系（如 init → execute → getResult）
- 接口协同完成一个完整功能流程（如 create → configure → start）
- 接口之间存在状态变化关系（如 setConfig → getConfig 验证）

#### 3.3 空值与异常场景设计规范

**空值场景（Null/Undefined/Empty）**：
- 传入 `null` 作为参数，验证接口是否抛出异常或返回安全默认值
- 传入 `undefined`，验证默认参数处理逻辑
- 传入空字符串 `''`、空数组 `[]`、空对象 `{}`

**异常/边界值场景（Exception/Boundary）**：
- 传入类型不匹配的参数，验证类型校验能力
- 传入超限值，验证边界处理
- 传入特殊值（`NaN`、`Infinity`），验证特殊数值处理

**大数据场景（Large Data）**：
- 传入大数组（10000+ 元素），验证性能和正确性
- 传入大字符串（10000+ 字符），验证长字符串处理能力
- 验证大数据场景下不发生内存溢出、栈溢出或超时

#### 3.4 用例编号规则

- 用例序号采用三位补零格式：`001`、`002`、`003`...
- 序号按模块分组递增，便于管理

### 阶段四：生成 XTS 用例描述文档

#### 4.1 文档结构

```markdown
# {库名} 未覆盖接口 XTS 用例描述

## 1. 概述
- 库名称、文档生成时间、基于文档（覆盖率报告文件名）
- 未覆盖接口总数：N、可测试接口数：T、不可测试接口数：N-T
- XTS 用例总数：C_cases
- 补充前覆盖率：X%、补充后预期覆盖率：100%

## 2. 接口可测试性分析

### 2.1 可测试接口（T 个）

| 接口名称 | 类型 | 测试方式 | 说明 |
|---------|------|---------|------|
| xxx | method | 直接调用 | 功能描述 |

### 2.2 不可测试接口（N-T 个）

| 接口名称 | 类型 | 原因 |
|---------|------|------|
| xxx | property | 涉及 UI |

## 3. 用例索引表

| 序号 | 用例名称 | 涉及接口 | 模块 |
|------|---------|---------|------|
| 001 | 基础功能验证 | methodA(), methodB() | 模块A |

## 4. XTS 用例详细描述

### 用例 001：{用例名称}

**用例描述**
[2~4 句话描述测试目的和验证的功能]

**用例预期结果**
1. 调用 `{接口签名}` 传入 `{参数}`，预期返回 `{值}`
2. 调用 `{接口签名}` 传入空值/null，预期返回默认值或不崩溃

**对应的函数接口**
- `{接口签名1}` — {调用说明}
- `{接口签名2}` — {调用说明}
```

#### 4.2 文件命名与存放

```
文件命名规则：{库名}未覆盖接口XTS用例描述.md
存放位置：覆盖率报告所在目录（或指定 outputDir）
```

#### 4.3 文档验证

生成文档后进行以下验证：

1. **内容真实性**：所有接口签名、功能描述与覆盖率报告严格一致
2. **可测试性判断准确性**：不可测试接口未生成用例
3. **预期结果可验证性**：每个用例的预期结果具体、可验证
4. **接口关联合理性**：多接口用例的接口间存在明确关联关系
5. **覆盖率报告自包含**：覆盖率报告的未覆盖清单已包含签名和功能描述，无需额外读取接口规格文档

## 常见问题处理

### Q1: 如何判断接口是否可测试？

参考阶段二的"可测试性判断标准"，核心判断依据：
- 是否为纯函数（输入固定 → 输出可预测）
- 是否涉及 UI 操作
- 是否可通过执行结果验证功能正确性

### Q2: 某接口依赖网络请求，是否可生成用例？

可生成用例，但需在用例描述中注明"需要 Mock 网络请求或使用测试服务器"。

### Q3: 多个接口如何组合到一个用例中？

参考阶段三的"多接口用例设计"，确保接口间存在调用依赖关系、协同完成功能流程或状态变化验证关系。

### Q4: 如何设计空值/异常/边界值用例？

参考阶段三的"空值与异常场景设计规范"，为每个接口规划空值、异常、边界值、大数据场景。参考 [references/TEMPLATE.md](references/TEMPLATE.md) 和 [references/EXAMPLES.md](references/EXAMPLES.md)。

## 注意事项

1. **结构体/组件不测**：`@Component struct` 标记的 UI 组件不生成 XTS 用例
2. **类型定义不测**：`interface`/`type` 仅类型声明，不生成用例
3. **Native 慎重**：`lib*.so` 导出的函数需要 ArkTS 层的 wrapper 才能测试
4. **枚举可测**：枚举值可通过 `import { EnumName } from 'library'` 后验证值
5. **setter/getter 配对**：有 `setXxx()` 和 `getXxx()` 的接口合并为一个用例
6. **Mock 标注**：依赖外部资源的接口，在用例描述中标注 Mock 要求
