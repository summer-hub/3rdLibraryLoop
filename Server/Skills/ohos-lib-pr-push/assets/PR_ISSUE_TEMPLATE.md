# PR / Issue / 报告模板（ohos-lib-pr-push）

本文件包含四段内容：Issue 模板渲染规则、Issue body 默认模板、PR body 模板、最终报告模板。`{占位符}` 由执行时填充。

> 约定：**源仓库配置了 Issue 模板时（Phase 1.6 探测 `source != none`），Issue 标题与 body 必须按「Issue 模板渲染规则」生成，跳过默认模板**；无模板时（cpf-rn / cpf-flutter 等）用 `[类型] {摘要}` 标题 + 下方 Issue Body 默认模板（字段结构与 [PR_CHECKLIST.md](PR_CHECKLIST.md) 的 Issue 必填内容对齐）。两种情况都禁止 `[auto]` 等无意义前缀；PR body 一律按 [PR_CHECKLIST.md](PR_CHECKLIST.md) 的 PR 描述模板生成；所有 body 临时文件写入 `/tmp`，流程结束后删除——工作目录只产出最终报告一个文档。

---

## 一、Issue 模板渲染规则（源仓库有模板时使用）

模板为 GitHub Issue Forms YAML（`get-issue-templates` 返回的 `templates[].yaml`），渲染成 API 可提交的 markdown body。

### 字段类型映射

| YAML `body[]` 项 | 渲染为 markdown | 说明 |
|------------------|----------------|------|
| `type: markdown` | `value` 原文 | 致谢/引导文字，原样保留 |
| `type: textarea` | `### {label}` + 正文 | `description`/`placeholder` 有助理解时以 `> ` 引用块附上；正文填真实内容 |
| `type: input` | `### {label}` + 正文（单行） | 同上 |
| `type: checkboxes` | 逐条 `- [x] {label}` | 自动提交场景默认全勾选 |

### 硬性规则

1. `validations.required: true` 的字段**必须填充基于 Phase 2 修改点总结的真实内容**，禁止留空、禁止原样保留 placeholder
2. 非必填字段无合适内容时填 `无`，不删除字段（保持模板结构完整）
3. 模板字段之外的补充内容（修改点清单、自动创建标记）追加到 body 末尾 `---` 分隔线之后
4. 标题按模板 `title` 字段格式生成（如 `[Bug]: 【等级：严重】【分类：功能】【三方库版本 1.0.1】【组件 LottieView】【属性 src】xxx 不生效`，`【】` 内占位符替换为真实值）

### 渲染示例（以 `缺陷反馈|Bug` 模板为例）

```markdown
感谢对三方库社区的支持与关注，欢迎反馈缺陷。

### 发生了什么问题？

{基于修改点总结的问题现象，具体到模块/场景}

### 期望行为是什么？

{修复后期望的正确行为}

### 如何复现该缺陷？

【预置条件】{...}
【测试步骤】{...}

### 三方库版本。

{从 workspaceDir 的 oh-package.json5 / package.json 读取的版本}

### 涉及编译环境信息，请补充。

无

### 堆栈跟踪或日志

{如有则粘贴关键堆栈；无则填"无"}

### 其他补充信息

无

### 提交前检查清单

- [x] 搜索现有 Issue，避免重复提交
- [x] 使用正确的 Issue 模板
- [x] 提供清晰的复现步骤（Bug 类）
- [x] 附上相关日志、截图或代码片段
- [x] 说明环境信息（操作系统、版本号等）
- [x] 检查标题是否清晰且包含类型前缀

---

### 修改点

| 序号 | 文件路径 | 修改类型 | 修改说明 |
|------|---------|---------|---------|
| 1 | {path} | 修改 | {具体修改说明} |

> 此 Issue 由 ohos-lib-pr-push 工作流按「{模板 name}」模板自动创建
```

> `新需求|Feature`（`[新需求]: `）、`问题咨询|Question`（`[Question]: `）等其他模板同理：按其 `body[]` 逐项渲染，`required` 字段必填。

## 二、Issue Body 默认模板（源仓库无模板时使用，字段与 PR_CHECKLIST 对齐）

> 标题格式 `[类型] {摘要}`（类型：`Bug`/`新需求`/`咨询`/`文档`/`工程化`/`重构`，如 `[Bug] ScrollView 在 xxx 场景上滑动卡顿`）。正文按下方模板填写；**bug 类**复现步骤/预期结果/实际结果/复现概率为必填，**需求/咨询类**删除不适用小节（保留问题描述、影响范围或应用场景）。

```markdown
## {一句话说明本次提交的作用}

### 问题描述

{详细说明遇到的现象/需求背景：为什么改、解决什么问题、达到什么效果}

### 复现步骤

1. {逐步操作，确保可重现；需求/咨询类删除本节}

### 预期结果

{期望的正确行为}

### 实际结果

{当前错误行为}

### 复现概率

{必现（100%）/ 高频 / 偶发}

### 环境信息

{框架&库版本、系统版本、设备型号等；从 workspaceDir 的 package.json / oh-package.json5 读取库版本，其余可得的如实填写，不可得写"未提供"}

### DEMO（如有）

{最小代码段 / 复现工程链接；无则删除本节}

### 日志/截图（如有）

{报错日志、堆栈；无则删除本节}

### 影响范围

{受影响的功能模块/场景}

### 修改点

| 序号 | 文件路径 | 修改类型 | 修改说明 |
|------|---------|---------|---------|
| 1 | {path} | 新增/修改/删除 | {具体修改说明} |

---
> 此 Issue 由 ohos-lib-pr-push 工作流自动创建
```

## 三、PR Body 模板（按 PR_CHECKLIST 描述模板，所有仓库通用）

> 依据 [PR_CHECKLIST.md](PR_CHECKLIST.md) 第三章模板，**删除不适用的章节**（如纯文档类 PR 删除根因分析/测试小节并说明不适用）。测试工程名按实际填写（RN 库为 RNT 工程，Flutter 库为对应测试工程）。Checklist 勾选原则：**本流程能保证/已验证的项勾选 `[x]`；需外部确认的项（AI 扫描、手动验证）保持 `[ ]` 并括注说明**，禁止无凭据全勾。

```markdown
## 修改点

{简述各文件/commit 修改了什么，基于 Phase 2 修改点清单，2-5 句 + 关键文件列表}

## 根因分析

{问题产生的原因与结果：代码存在 xxx 缺陷，导致了 xxx 问题。需求/文档类删除本节}

## 方案说明（AI输出）

- **修改方案说明**：{如何修复/实现}
- **影响范围说明**：{受影响的模块/接口}
- **兼容性分析说明**：{是否 Breaking Change、对既有调用方的影响}

## 测试情况

### 新增测试用例

- 本工程 {分支} `<path>/<test-file>` → ✅ 通过
- {RNT|测试工程名} {分支} `<path>/<test-file>` → ✅ 通过

### 触发的已有测试用例

{已有用例可覆盖本次修改时列出；本次修改即用例/demo 补充时写"本次提交内容即为用例补充，见上方修改点"；均不适用则删除本节}

### 手动验证

- [ ] 已验证修复有效{（有验证结论时勾选并附结果）}
- [ ] 已确认不影响其他功能

## 资料修改

- 是否已在README说明该接口/功能的变化：是/否/不涉及
- 是否已在README和package.json修改了版本信息：是/否/不涉及

## 依赖关系变更

{依赖变更说明（需依赖 三方库xxxx版本 / 框架xxx版本解决）；无变更写"无"}

## 关联 Issue

Closes #{issue_number}（[#{issue_number}]({issueUrl})）

---

## Checklist

- [x] 已关联 Issue（issue编号&超链接）
- [x] Issue 包含：问题描述、复现步骤、预期结果、实际结果、环境信息
- [x] 根因分析和方案说明已补全
- [x] 修复代码与测试用例同步提交
- [x] 已列出触发的用例及运行结果
- [ ] 已通过 AI 扫描评审（{已通过 pr-check 扫描 / 待人工或 AI 流程确认}）
- [x] 所有测试用例通过
- [x] 兼容性影响和依赖关系影响已完成分析

---
> 此 PR 由 ohos-lib-pr-push 工作流自动生成
```

> **必须**：`Closes #{issue_number}` 在创建 PR 时写入 body，不做事后 PATCH。
> AI 扫描状态如实填写：上游已跑 pr-check（AI 代码扫描）则勾选并注明；未知/未执行保持 `[ ]` 括注，不得虚勾。

## 四、最终报告模板（ohos-lib-pr-push-report.md）

```markdown
# 三方库自动提 PR 报告

## 基本信息

| 项目 | 内容 |
|------|------|
| 源仓库（上游） | {upstreamUrl} |
| fork 仓库 | {forkRepoUrl} |
| 提交模式 | fork → 源仓库跨仓 PR |
| 工作分支（PR head） | {当前分支}（未切换分支） |
| 分支推送状态 | 新推送 / 已推送（跳过 commit/push）/ 分叉（终止，禁强推） |
| 幂等检测 | 未发现已有 open PR / 发现同源 open PR（{prUrl}，已终止） |
| PR 目标分支（base） | {上游同名分支 / default_branch（回退时标注）} |
| 执行时间 | {currentTime} |

## 执行结果

| 项目 | 内容 |
|------|------|
| 状态 | 成功 / 失败（{失败阶段}） |
| PR 地址 | {prUrl} |
| PR 编号 | !{prNumber} |
| Issue 地址 | {issueUrl} |
| Issue 编号 | #{issueNumber}（标题：{issue 标题}） |
| Issue 模板 | {模板 name}（来源：仓库级/组织级 {owner}/.gitcode）/ 未配置模板（默认规范字段，PR_CHECKLIST 对齐） |
| Issue 绑定 | 是 / 否（PR body 含 `Closes #{issueNumber}`） |
| CI 触发 | 是 / 否（评论 `Start build` 于原仓库 PR） |
| 测试同步 | 新增用例 {N} 条 / 已有用例覆盖（列于 PR body）/ 本次提交即用例补充 / 不适用（{原因}） |
| AI 扫描 | 已通过（上游 pr-check）/ 未执行（PR body 已如实括注） |
| CHANGELOG | 已更新（英文条目含 Issue 链接）/ 跳过（未修改三方库内部源码） |

## 修改文件清单

| 序号 | 文件路径 | 修改类型 | 修改说明 |
|------|---------|---------|---------|
| 1 | {path} | 新增/修改/删除 | {具体修改说明} |

## CHANGELOG 更新

{判定为"需要"时：写入 CHANGELOG.md 的英文条目原文（含 Issue 链接）；判定为"不需要"时：跳过原因，如"本次仅涉及 demo 页面与测试用例，未修改三方库内部源码"}

## 错误信息

{如有失败步骤：失败阶段、原因、已完成的产物编号与链接}
```
