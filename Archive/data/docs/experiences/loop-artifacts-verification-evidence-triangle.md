## 跨循环产物复用核验的证据三角模式与汇总指标分解

### 问题现象
"loop N 复用 loop N-1 产物"的核验任务中存在两类陷阱：
1. 仅凭前序步骤报告的"成功"结论即判定通过，报告与实物可能不一致；
2. 任务描述中的汇总数字（如"设备端 95/95，共 154/154"）在前序报告中没有直接对应的单一数字，只对总数会漏掉口径错配。

### 解决方案
**证据三角模式**——关键声明必须三方交叉验证：
1. 报告声明：读前序步骤报告结论；
2. 实物产物：文件存在性 + 大小 + 时间戳（如 HAR 22MB / tgz 44MB / 签名与未签名 HAP 实体文件）；
3. 现场 git/文件查询：如 `git merge-base br_rnoh0.84 br_rnoh0.82` 实测分支血缘、直接读依赖清单文件原文、实际列目录比对测试文件清单（jest.config.js、__mocks__/、src/__tests__/、example/src/suites/ 逐一对账）。

**汇总指标分解规则**：验收标准含汇总数字时逐项拆解到报告分项对账。示例："95/95" = 自动套件 85/85 + Hooks 探针 10/10；"154/154" = Jest 59 + 85 + 10，分解后才确认口径一致。

**自动生成产物权威级规则**：链路中自动生成的 diff/扫描件（如 rn-scan-exports.cjs 生成的 api-diff_*.md）存在已知偏差（对 Nitro HybridObject 架构，Spec 文件为 `*.nitro.ts` 而非 `Native*.ts` 命名，扫描器规则不覆盖，导致"TurboModule Spec 变更：无"误判）。若后续人工分析报告已修正，验收一律以修正结论件为准，自动件仅作参考——否则会拿错误基线对账。

### 结果
react-native-mmkv loop0 产物核验 5/5 通过：分支血缘（merge-base = 预期 commit c047ada）、编译产物、依赖版本、测试产物（与报告清单一一对应）均经实物交叉验证，测试口径 59+85+10=154 分解对账一致。可复用结论：任何"loop N 复用 loop N-1 产物"的核验任务，直接套用证据三角模式与汇总指标分解规则。
