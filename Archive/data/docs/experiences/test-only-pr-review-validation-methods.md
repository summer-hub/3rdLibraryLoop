## 测试型 PR 的三层交叉验证法与合规检查

### 问题现象
纯测试补充型 PR（不修改库源码）的检视核心是"验证测试本身正确"，但测试文件的正确性无法仅凭 diff 判断：导入符号可能不存在、构造函数签名可能与库源码不匹配、内嵌测试夹具数据可能损坏或与断言不符；同时此类 PR 极易遗漏 License 头等合规项（开发者注意力集中在用例逻辑上）。

### 解决方案
**三层交叉验证法**：
1. **导入符号核验**：深路径导入（`@ohos/xxx/src/main/ets/...`）逐一确认目标文件存在；根入口导入确认在 `library/index.ets` 导出面中；深路径导入若为仓库既有模式（grep 既有测试确认），不作为问题上报。
2. **构造函数签名比对**：测试调用与库源码构造签名逐一比对（参数数量、类型、顺序）。
3. **夹具数据解码核验**：对 base64 内嵌夹具本地解码（python3 + base64），核验文件头/长度/关键 offset/关键字节与测试断言值吻合。

**配套检查**：
- 测试脚手架与库内部契约的链路自洽验证：如 TestAbility 写入 `GlobalContext.setValue('path', filesDir)` 须与库内 `Mp3File.save()` 读取 `GlobalContext.getContext().getValue("path")` 的键精确对应——此类依赖库未文档化行为的链路必须到库源码中确认，否则测试在其他环境可能静默失败。
- 未使用导入检测：对测试文件按 import 符号 grep 计数（出现 ≤1 次即未使用）。
- License 头一致性：对照仓库既有测试文件的头格式，新文件缺失即报合规问题（OAT 扫描风险）。
- 测试文件头注释与实现一致性：夹具机制注释（如"从 rawfile 复制"）与实际实现（base64 内嵌解码）不符会误导维护者，应抽查。

### 结果
在 mp3agic PR #53（10 个新增测试文件）检视中：三层验证全部通过（4 个 base64 夹具解码后与断言吻合、全部构造签名一致），确认测试内容质量优秀；同时发现 10 个文件全部缺失 License 头（Major）、1 处 arkts 违规（Major）、1 处冗余导入（Minor），最终判 CONDITIONAL，并给出"补 License 头 + 1 行类型标注即可升至 PASS"的低成本修复路径。**分级经验**：测试型 PR 的问题通常集中在合规与代码卫生而非功能，分级时应避免因"零功能风险"直接放行 PASS。
